# Handoff — cutting v0.2.0, the release workflow's first real execution

**Date:** 2026-08-31

## Scope

`.github/workflows/release.yml` shipped in PR #3 with its YAML half unexecuted — recorded there as
that change's riskiest claim, and left unvalidated. This records what happened when it finally ran.

## What happened

**Attempt 1 published nothing, and looked like success.** The tag was pushed from a pre-existing
local clone whose `main` had never been pulled, so it landed on `94a2860` — the commit before
PR #3 and #5 merged. The terminal printed `* [new tag] v0.2.0 -> v0.2.0`.

- `git ls-tree -r --name-only 94a2860` contains neither `CHANGELOG.md` nor
  `.github/workflows/release.yml`.
- Workflow runs for `release.yml` after that push: **0**.
- Releases after that push: **none**.

GitHub runs the workflow *as it exists at the tagged commit*. There was no workflow there, so
nothing ran, nothing failed, and nothing reported. This is the one failure shape the mechanism
cannot catch by design: the fail-closed check that makes a missing changelog section abort the
release lives *inside* the job that never starts.

**Attempt 2 worked on the first try.** After deleting the tag and re-tagging the merge commit
`0824018`: run #1 completed **success**, and the published release body is the `[0.2.0]` section
of `CHANGELOG.md` verbatim, authored by `github-actions[bot]`.

Release workflow publishes the changelog section matching the tag · STATUS: VALIDATED · evidence:
release `v0.2.0`, `Release` workflow run #1 on `0824018`.

## Material decisions

- **The procedure now tags `origin/main` by name rather than local `HEAD`.** An earlier draft of
  the fix told the operator to `git pull` and eyeball `git log -1`. Codex round 1 on PR #6 showed
  that is insufficient: `git pull` reports "Already up to date" when the branch is *ahead*, so an
  unpushed local commit passes the check and gets tagged, publishing a release from a commit absent
  from the default branch. `--ff-only` does not reject that case either. Naming the remote-tracking
  ref removes local state from the decision entirely.

## Rejected inference — recorded so it is not re-adopted

**"A tag push writing more than one object means you tagged the wrong commit."** Attempt 1 wrote 37
objects and attempt 2 wrote 1, which made this look like a reliable staleness tell. It is not. In
the ordinary stale-clone case both the stale commit and the current tip are already on the remote,
so tagging either transfers only the tag object. A high object count means some reachable objects
are missing remotely — not that the commit is out of date — so the "diagnostic" would have
stayed silent on exactly the mistake it claimed to catch.

The 37 objects in attempt 1 were never traced to a cause; that clone was not available for
inspection. An unexplained observation generalized into a rule is the failure the evidence grammar
exists to prevent, and it was drafted into `CHANGELOG.md` before review caught it.

Object count is not a valid staleness diagnostic for tag pushes · STATUS: REJECTED · evidence:
this handoff, PR #6 round-1 review.

## Not done

- **`v0.1.0` remains untagged**, and should stay that way unless someone publishes its release by
  hand: that commit predates the workflow, so tagging it would reproduce attempt 1 exactly.
